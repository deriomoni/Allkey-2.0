# Восстановление базы allkey из резервной копии

Пошаговая инструкция для **не-разработчика**. Все команды выполняются на сервере
(вход по SSH). Копируйте их целиком. Если что-то идёт не так, как описано, —
**остановитесь и позовите специалиста**, а не пробуйте наугад.

> ⚠️ Восстановление **заменяет** текущие данные в базе на данные из копии. Всё, что попало
> в базу после создания этой копии, будет потеряно. Поэтому сначала — обязательно шаг 2.

Ниже `/opt/allkey` — папка, где лежит проект (там `docker-compose.prod.yml`). Подставьте свой путь.

---

## Шаг 1. Зайти на сервер и перейти в папку проекта

```bash
ssh пользователь@адрес-сервера
cd /opt/allkey
```

## Шаг 2. Сделать свежий дамп «на всякий случай» (страховка перед заменой)

Даже если база повреждена — снимок текущего состояния лишним не будет.

```bash
sudo ./pg_backup.sh
```

## Шаг 3. Найти нужную копию во внешнем хранилище

```bash
sudo rclone ls allkey-backup:allkey/db
```

Вы увидите список файлов вида `allkey-<база>-ГГГГММДД-ЧЧММСС.sql.gz`. Дата и время — в имени.
Выберите копию **за нужную дату** (обычно — самую свежую перед моментом, когда всё сломалось).

## Шаг 4. Скачать выбранную копию на сервер

Подставьте имя файла из шага 3 вместо `<ИМЯ_ФАЙЛА>`:

```bash
sudo rclone copy "allkey-backup:allkey/db/<ИМЯ_ФАЙЛА>" /var/backups/allkey/
ls -lh /var/backups/allkey/<ИМЯ_ФАЙЛА>
```

Вторая команда должна показать файл и его размер (не 0 байт).

## Шаг 5. Остановить приложение (чтобы никто не писал в базу во время замены)

```bash
sudo docker compose -f docker-compose.prod.yml stop backend frontend
```

Базу (`db`) **не останавливаем** — из неё будем восстанавливать.

## Шаг 6. Восстановить данные из копии

Подставьте то же имя файла. Команда распаковывает копию и заливает её в базу.
Имя базы и пользователя берутся из файла `.env` автоматически.

```bash
set -a; source /opt/allkey/.env; set +a
gunzip -c /var/backups/allkey/<ИМЯ_ФАЙЛА> \
  | sudo docker compose -f docker-compose.prod.yml exec -T \
      -e PGPASSWORD="$POSTGRES_PASSWORD" db \
      psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"
```

Пойдут строки вроде `DROP TABLE`, `CREATE TABLE`, `COPY …` — это нормально, идёт заливка.
Отдельные `NOTICE`/`does not exist` в начале — не ошибка (копия сначала убирает старое).

## Шаг 7. Запустить приложение обратно

```bash
sudo docker compose -f docker-compose.prod.yml start backend frontend
```

## Шаг 8. Проверить, что сайт работает

- Откройте сайт в браузере, войдите, посмотрите, что данные — из нужной копии.
- Если нужно заглянуть в базу напрямую (число записей в таблице компаний, например):

```bash
set -a; source /opt/allkey/.env; set +a
sudo docker compose -f docker-compose.prod.yml exec -T \
  -e PGPASSWORD="$POSTGRES_PASSWORD" db \
  psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "\dt"
```

---

## Если что-то пошло не так

- **Приложение не поднялось** после шага 7 — посмотрите логи:
  `sudo docker compose -f docker-compose.prod.yml logs --tail=50 backend`
- **Ошибка про пароль/пользователя** на шаге 6 — значит `.env` не прочитался или в нём другие
  значения. Проверьте: `grep POSTGRES /opt/allkey/.env`
- **Не уверены, что копия правильная** — не заливайте в рабочую базу. Разверните её сначала на
  отдельной тестовой базе и посмотрите. Это уже задача разработчика — позовите его.

## Как убедиться заранее, что восстановление вообще работает

Не ждите аварии. **Раз в месяц** разработчик должен разворачивать свежую копию на тестовой
базе и проверять, что данные читаются. Копия, из которой ни разу не восстанавливались, может
оказаться битой — и вы узнаете об этом в самый неподходящий момент.
