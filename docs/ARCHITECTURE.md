# Архитектура Allkey 2.0

Карта репозитория для того, кто видит проект впервые: стек, как устроены модули,
как добавить новый, что нельзя ломать. Обновлено 18.08.2026.

Файл описывает **устройство**, а не задачи. Состояние работ — в `ZADANIE-*.md`
и в досье проекта, которое владелец носит между сессиями.

---

## 1. Стек и запуск

| Слой | Что используется |
|---|---|
| Бэкенд | Python 3.11 (в образе), FastAPI 0.109, SQLAlchemy 2.0, PostgreSQL 15 через psycopg2 |
| Аутентификация | JWT на `python-jose`, пароли — `passlib[bcrypt]` |
| Разбор файлов | pandas, openpyxl, xlrd; генерация документов — docxtpl |
| Фронтенд | React 18 + TypeScript, Vite, react-router-dom v6, axios |
| Стили | **UI-кита и CSS-фреймворка нет.** Общие классы в `frontend/src/index.css`, точечная вёрстка — инлайновые `CSSProperties`. Стейт-менеджера нет: `useState` плюс один контекст `AuthContext` |
| Инфраструктура | docker-compose (`dev` / `prod` / `test`), nginx, `init-ssl.sh` |

Запуск для разработки — `docker-compose up`: `db` (postgres:15-alpine), `backend`
(uvicorn), `frontend` (vite). Локальный Python на машине владельца — 3.13, а
зависимости запинованы под 3.11, поэтому **бэкенд поднимается только в Docker**;
тесты гоняются в отдельном venv с 3.13-совместимыми колёсами.

Конфигурация — `backend/app/config.py`, pydantic-settings из `.env`:
`database_url`, `secret_key`, `algorithm`, `access_token_expire_minutes`.
CORS-origins читаются из переменной `CORS_ORIGINS` в `main.py`.

## 2. Как устроен бэкенд

`backend/app/` — один каталог на домен, внутри одинаковый набор файлов:

```
<домен>/
  router.py     эндпоинты (APIRouter с prefix и tags)
  schemas.py    pydantic-модели запросов и ответов
  models.py     таблицы SQLAlchemy (если домен что-то хранит)
  ...           доменные модули: services, helpers, generator, context
  tests/        pytest
```

Домены:

| Домен | Назначение | Хранит в БД |
|---|---|---|
| `auth` | `/auth/login`, `/auth/register`, выпуск JWT, `get_current_user` | — |
| `users` | профиль и админский CRUD пользователей | `users` |
| `licenses` | тарифы и лицензии | `license_plans`, `user_licenses` |
| `settings` | настройки сайта (публичные и админские) | `site_settings` |
| `services` | **реестр модулей и доступ к ним** — см. §4 | `services`, `service_access`, `user_service_overrides` |

**Персональная выдача сильнее роли — и это рабочий инструмент, а не тонкость.** Запись
в `user_service_overrides` перебивает и наличие, и отсутствие роли. Практическое следствие:
показать модуль **одному человеку**, не открывая его всей роли, можно — это отдельная
выдача на экране «Доступы», код при этом не трогается. Так же можно точечно закрыть модуль
конкретному пользователю, оставив его открытым для остальных. Для беты с одним проверяющим
это ровно тот механизм, который нужен: `roles: []` плюс персональная выдача по мере
надобности.
| `reconciliation` | три сверки: case1, case2, case3 | — (см. §6) |
| `personnel` | кадровые документы (`hr`) | `Company`, `DocumentTemplate` |
| `f10104` | помогайка по форме 101.04 (внутренняя бета) | — |

`backend/app/changelog/` — пустой каталог, оставшийся от удалённого домена.
Кода в нём нет, в `main.py` он не подключён.

### Сборка приложения

`backend/app/main.py` — единственное место, где всё сходится:

1. импорт моделей ради регистрации в метаданных (`import app.<домен>.models  # noqa: F401`);
2. `Base.metadata.create_all(bind=engine)` — создание таблиц;
3. `lifespan`: `seed_services(db)` и фоновая задача очистки временных файлов;
4. `app.include_router(...)` по одному вызову на роутер.

**Забыть импорт моделей в `main.py` — значит не получить таблицы.** Это не
догадка, а способ, которым в проекте заменена миграционная система.

### Схема БД: Alembic не используется

Таблицы создаются через `create_all`, наполнение справочников — идемпотентная
функция в `lifespan`. Alembic лежит в `requirements.txt`, но не подключён и не
применяется.

`create_all` умеет только добавлять таблицы, а не колонки. Поэтому для
аддитивных правок есть `backend/app/personnel/schema_sync.py`:
`ensure_personnel_schema(engine)` добавляет недостающие колонки перед стартом.
Правила там жёсткие: только `ADD COLUMN`, колонка обязана быть nullable или
иметь server_default, каждое изменение логируется. Первое неаддитивное
изменение — повод переходить на Alembic, а не обходить синхронизатор.

## 3. Как устроен фронтенд

```
frontend/src/
  App.tsx            маршруты и ProtectedRoute
  auth/AuthContext   пользователь, токен, список доступных сервисов
  api/client.ts      единственный axios-инстанс + по объекту API на домен
  components/        Layout (шапка и меню), модалки, общие виджеты сверок
  pages/             по странице на модуль
  index.css          все общие классы
```

`api/client.ts` — один `axios.create` с интерцепторами: подстановка
`Authorization` из localStorage и сброс токена на 401. Каждый домен добавляет
туда свой объект (`reconciliationApi`, `personnelApi`, `servicesApi`, …).

**Меню строится из данных, а не из кода.** `Layout.tsx` рисует пункты по
списку `services` из `AuthContext` — тому, что вернул бэкенд для текущего
пользователя, — и сам добавляет бейдж `beta` при `status === 'beta'`. Новый
модуль в меню не прописывается руками.

## 4. Доступ к модулям — реестр сервисов

Ключевой механизм проекта. Живёт в `backend/app/services/`.

| Таблица | Смысл |
|---|---|
| `services` | `code`, `title`, `description`, `status` (`beta` \| `production`), `is_enabled` — глобальный выключатель, `sort_order` |
| `service_access` | какие **роли** видят сервис: строка на пару (сервис, роль) |
| `user_service_overrides` | персональное `allow` для конкретного пользователя — **сильнее роли** |

Порядок проверки в `user_has_service` (`services/dependencies.py`):

1. `admin` → всегда доступ, включая `beta` и выключенные сервисы;
2. сервиса нет или `is_enabled = False` → отказ;
3. персональный override → его значение;
4. есть `service_access` для роли пользователя → доступ;
5. иначе отказ.

Гейт на эндпоинте — `Depends(require_service("код"))`, отказ — **403**.
На фронте `<ProtectedRoute service="код">` — это только UX; настоящая проверка
всегда на бэкенде.

**Отдельные feature flags не нужны.** Закрытая бета = запись в `SEED_SERVICES`
со `status: "beta"` и ролями без `client`. Раскрытие сервиса — правка строки в
реестре через админский экран «Доступы», а не релиз.

### Роли и лицензии независимы

- **Роль** (`admin` / `employee` / `client`) отвечает на вопрос «какие сервисы видно».
- **Лицензия** отвечает на вопрос «оплачен ли доступ».

Связывать их нельзя. Саморегистрация всегда даёт роль `client` (самый первый
пользователь системы — `admin`); сотрудников заводит владелец через `POST /users`.

## 5. Как добавить новый модуль

1. `backend/app/<код>/` по образцу существующего домена: `router.py`,
   `schemas.py`, при необходимости `models.py` и `tests/`.
2. Все эндпоинты — под `Depends(require_service("<код>"))`.
3. Запись в `SEED_SERVICES` (`services/router.py`): `code`, `title`,
   `description`, `status`, `sort_order`, `roles`.
4. В `main.py`: `app.include_router(...)`, а если есть модели — ещё и
   `import app.<код>.models  # noqa: F401`.
5. Фронтенд: страница в `pages/`, маршрут в `App.tsx` внутри
   `<ProtectedRoute service="<код>">`, объект API в `api/client.ts`.
   В `Layout.tsx` ничего не правим — меню возьмёт пункт из реестра.
6. Тесты в `<код>/tests/` **плюс расширение `testpaths` в `backend/pytest.ini`** —
   иначе pytest их не увидит.
7. Обязательный `test_gating.py` по образцу `personnel/tests/test_gating.py`:
   без токена → 401, чужая роль → 403, `employee` → 200, `admin` → 200.

Образец выбирается по жанру модуля:

- «два файла → таблица расхождений» → `reconciliation` + `Case1Page.tsx`;
- «форма → расчёт → документ» → `personnel` + `HrPage.tsx`.

## 6. Соглашения, которые легко нарушить по незнанию

**Stateless по требованию владельца, а не по недоделке.**
Сверки не хранят загруженные файлы: они живут в эфемерном каталоге контейнера
(`SESSION_STORAGE_DIR`, по умолчанию `/tmp/reconciliation_sessions`) и чистятся
фоновой задачей — файлы через 10 минут, результаты через 30.
Модуль `personnel` не хранит персональные данные сотрудников вообще: форма
живёт в черновике браузера и уходит в теле POST только ради рендера документа.
В БД остаются лишь реквизиты работодателя из открытого реестра и шаблоны.
Это продано как преимущество продукта — «чинить» нечего.

**Персональные данные — только в теле запроса.** ИИН, номера документов и
подобное не должны попадать в path/query и в логи.

**Тексты интерфейса — по-русски.** Сообщения об ошибках пишутся для бухгалтера,
а не для разработчика.

**Комментарии в коде — по-английски**, как в существующих модулях.

**Ставки и справочники — в данных, а не в коде.** Константы года лежат в
`personnel/rates.py` (`RatePeriod` с окном действия), налоговые справочники
101.04 — в `f10104/data/rules_101_04.json`. Переход на следующий год должен
быть правкой данных, а не релизом.

**`.gitignore` шире, чем кажется:** игнорируются `data/`, `*.xlsx`, `*.xls`.
Файлы приложения, попадающие под эти шаблоны, добавляются исключениями —
см. существующие `!backend/app/personnel/templates/**` и
`!backend/app/f10104/data/**`. Git не умеет возвращать файл, у которого
исключён родительский каталог, поэтому исключать надо и каталог, и содержимое.

**Ветки и деплой.** Работа идёт в feature-веткам; в `main` вливает и
выкатывает на прод только владелец.

## 6а. Выкатка: сначала посмотреть, что развёрнуто

**Перед любой выкаткой первым делом смотрите, что реально развёрнуто на сервере.**
Не в коде, не по названию ветки, которую считаете основной, — заходите и смотрите.

```bash
ssh <сервер> "cd /root/co-founder-reconciliation-tool && git status -sb && git log --oneline -1"
```

Причина не теоретическая. 20.08.2026 выкатка помогайки готовилась в предположении, что прод
живёт на `main`. На сервере обнаружилось, что развёрнута ветка `feature/roles-and-access`,
и в ней восемь коммитов, которых в ветке помогайки не было: сверка банковских выписок,
сверка курсов валют, раздел «Обновления» — 2 420 строк в 18 файлах. **Выкатка ветки как есть
сняла бы эти разделы с живого сайта.** Обнаружилось бы это не тем, кто выкатывал.

Репозиторий живёт несколькими долгими ветками, и развёрнута не та, что считается основной.
Пока это так, предположение о ветке — источник ровно той аварии. Приведение веток к одной
линии — отдельная задача, и делать её в день выкатки нельзя: две изменённые вещи разом не
дают понять, какая из них сломалась.

**Порядок выкатки, проверенный 20.08.2026:**

1. посмотреть, что на сервере, и слить это в выкатываемую ветку, если расходится;
2. сделать бэкап базы: `pg_dump ... | gzip > /root/db-backups/before-<что>.sql.gz`;
3. `git fetch origin && git checkout <ветка> && docker compose -f docker-compose.prod.yml up -d --build`;
4. проверить **фактическое состояние базы**, а не код: реестр сервисов, выданные роли, таблицы;
5. прогнать один сквозной кейс на проде;
6. проверить, что прежние разделы на месте.

Замер: сборка и подмена контейнеров — 96 секунд, из них сайт недоступен несколько секунд.
Сборка идёт при работающем сайте. Откат — та же команда с прежней веткой, столько же времени.

**Осторожно с проверкой «страница открывается».** Фронтенд — SPA: nginx отдаёт `index.html`
на любой путь, и `curl` вернёт 200 даже для `/полная-ерунда`. Это не проверка. Проверять надо
либо наличием опознавательных строк в собранном бандле, либо реальным маршрутом бэкенда
(401 или 405 — маршрут есть, 404 — маршрута нет), либо глазами в браузере под учётной записью.

## 7. Тесты

`backend/pytest.ini` перечисляет `testpaths` явно — тесты вне этого списка
**не запускаются**. Сейчас там `app/personnel/tests` и `app/f10104/tests`.

Тесты не требуют PostgreSQL: `conftest.py` каждого модуля ставит
`DATABASE_URL` на in-memory SQLite до импорта `app.database`.
Фронтенд-тестов и CI в проекте нет; проверка фронтенда — `npm run build`
(включает `tsc`) и `npm run lint`.
