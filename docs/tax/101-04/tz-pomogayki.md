## 1. Что не так с первоначальной постановкой (и что меняем)

Разбор исходного наброска — не как критика, а как список решённых развилок. Каждый пункт отражён в дереве вопросов.

| # | Было в наброске | Проблема | Как в ТЗ |

## 2. Архитектура

```
┌─────────────────────────────────────────────────────────────────┐
│  UI: пошаговый визард (или чат-режим)                           │
│  ─ прогресс-бар, «назад», сохранение черновика                  │
│  ─ каждый ответ ⇒ подсказка + ссылка на статью НК               │
└────────────────────────┬────────────────────────────────────────┘
                         │ answers: {questionId: value}
┌────────────────────────▼────────────────────────────────────────┐
│  RULES ENGINE (чистая функция, без побочных эффектов)           │
│  evaluate(answers, refbooks, date) → Verdict                    │
│  ─ детерминированный, версионируемый                            │
│  ─ каждое правило возвращает {result, basis[], confidence}      │
└────────────────────────┬────────────────────────────────────────┘
                         │
┌────────────────────────▼────────────────────────────────────────┐
│  СПРАВОЧНИКИ (rules.json + БД)                                  │
│  countries · offshore_list · conventions · convention_rates     │
│  income_codes · treaty_codes · vat_place_rules · rates · mrp    │
│  fx_rates (кэш курсов НБ РК)                                    │
└────────────────────────┬────────────────────────────────────────┘
                         │
┌────────────────────────▼────────────────────────────────────────┐
│  ВЫВОД                                                          │
│  ─ Заключение (что делать, сколько, когда)                      │
│  ─ Заготовка строк 101.04 (значения граф приложения)            │
│  ─ Заготовка 300.04 (если применимо)                            │
│  ─ Чек-лист документов                                          │
│  ─ Красные флаги                                                │
│  ─ Нормативное обоснование (сворачиваемый блок)                 │
│  ─ Экспорт: PDF / печать / копирование в буфер                  │
└─────────────────────────────────────────────────────────────────┘
```

**Принципы:**

1. **Движок отделён от контента.** Ставки, коды, списки стран, тексты подсказок — в `rules.json`, не в коде. Обновление НК не требует релиза.
2. **Версионирование правил.** У каждого прохождения сохраняется `rules_version` и `answers` — чтобы можно было воспроизвести вывод спустя год и понять, почему помогайка так сказала.
3. **Три уровня уверенности вывода.** `confirmed` (норма подтверждена дословно) / `likely` (косвенно) / `manual_review` (норма спорна → помогайка не даёт вывод, а ставит флаг «нужна ручная проверка»). Уровень определяется статусом `[✓] [~] [!]` из базы знаний.
4. **Никогда не молчать о неопределённости.** Если правило `manual_review`, вывод показывает вопрос, а не ответ.
5. **Два обязательства считаются независимо.** КПН и НДС — параллельные ветки с разными периодами, датами и курсами. Нельзя выводить общий «квартал».

## 3. Режимы работы

| Режим | Точка входа | Сценарий |
|---|---|---|
| `mode=check` (основной) | «Проверить операцию с нерезидентом» | Одна операция → полный разбор КПН + НДС + 101.04 |
| `mode=batch` | «Собрать 101.04 за квартал» | Список операций за квартал → сводная форма 101.04 со всеми строками |
| `mode=fix` | «Я уже сдал / уже ошибся» | Диагностика ошибки + маршрут самокорректировки (дополнительная ФНО + 3 рабочих дня → освобождение по ст. 279 КоАП) |
| `mode=doc` | Загрузка документа (АВР, инвойс, контракт) | Извлечение полей → предзаполнение ответов → пользователь подтверждает/правит |
| `mode=free` | Свободное описание ситуации текстом | LLM-разбор → маппинг на ответы визарда → дальше стандартный поток |

> Режимы `doc` и `free` только **предзаполняют** ответы. Расчёт всегда выполняет детерминированный движок, никогда — модель. Это принципиально: налоговый вывод должен быть воспроизводим.

### Блок S4-А. Определение нормы и даты курса — движок решает сам

**Принцип.** Бухгалтер не выбирает подпункт статьи 684 и не отвечает на вопрос «начислено или выплачено». Он сообщает **факты**, которые знает без раздумий: когда подписан акт, когда ушли деньги, отнесена ли сумма на вычеты. Норму, дату курса, срок уплаты и квартал формы выводит движок и **показывает обратно словами**.

Причина: термины «начислено» и «выплачено» — источник самой частой ошибки начинающего бухгалтера. Помогайка существует затем, чтобы снять этот выбор, а не переложить его на пользователя в других словах.

**Что спрашиваем (только факты):**

| Ключ | Вопрос | Формат |
|---|---|---|
| **S4.1** | Дата подписания акта / принятия инвойса к учёту | date, либо «акта ещё нет» |
| **S4.2** | Дата перечисления денег нерезиденту | date, либо «оплаты ещё не было» |
| **S4.2a** | *(если оплата была и она раньше акта)* Оплачено полностью или частично | полностью / частично + сумма аванса |
| **S4.6** | *(если оплаты не было)* Отнесена ли сумма на вычеты в декларации по КПН | да + год декларации / нет |
| **S4.7** | Рассчитались ли встречной поставкой товаров, работ или услуг **резидента** | да / нет |

**Правила вывода — группа R-DATE.** Все ссылки на ст. 684 п. 1.

| Правило | Условие | Норма | Курс на дату | Срок перечисления |
|---|---|---|---|---|
| **R-DATE-01** | акт есть ∧ оплата есть ∧ оплата не раньше акта ∧ не встречная поставка | **пп. 1)** | **дата выплаты** | 25 к. д. после окончания месяца выплаты |
| **R-DATE-02** | оплата есть ∧ (акта нет ∨ оплата раньше акта) — аванс, доход ещё не начислен | **пп. 3)** | *дата начисления, пока неизвестна* | обязанность не наступила; в чек-лист контрольная дата |
| **R-DATE-03** | оплата есть ∧ оплата раньше акта ∧ акт уже подписан — аванс закрыт | **пп. 3)** | **дата начисления** | 25 к. д. после окончания месяца начисления |
| **R-DATE-04** | частичный аванс: часть оплачена до акта, часть после | **пп. 3) + пп. 1)** | **две даты**: на аванс — дата начисления, на остаток — дата выплаты остатка | два срока, считаются отдельно |
| **R-DATE-05** | расчёт встречной поставкой товаров, работ, услуг резидента | **пп. 4)** | **дата начисления** | 25 к. д. после окончания месяца начисления, в пределах суммы обязательств |
| **R-DATE-06** | акт есть ∧ оплаты нет ∧ отнесено на вычеты | **пп. 2)** | **последний день налогового периода** (31 декабря года декларации, п. 1 ст. 358) | 10 к. д. после срока сдачи декларации по КПН |
| **R-DATE-07** | акт есть ∧ оплаты нет ∧ на вычеты не отнесено | — | — | обязанность перечислить не наступила; в чек-лист контрольная дата |
| **R-DATE-08** | вознаграждения по долговым ценным бумагам и депозитам со сроком погашения позже 10 к. д. после срока сдачи декларации | **пп. 1)** вместо пп. 2) | дата выплаты | 25 к. д. после окончания месяца выплаты |

**Обязательный вывод обратно пользователю.** Определив норму, помогайка объясняет её словами, без терминов «начислено / выплачено» в роли вопроса:

> Акт подписан 20.02.2026, деньги перечислены 30.03.2026. Доход и начислен, и выплачен, поэтому применяется подпункт 1) пункта 1 статьи 684: курс берётся **на дату выплаты — 30.03.2026**, налог перечисляется до **25.04.2026**, операция попадает в форму 101.04 за **I квартал 2026**.

> Аванс перечислен 30.03.2026, акт ещё не подписан. Применяется подпункт 3): курс возьмётся **на дату начисления дохода**, а не на дату аванса, и срок пойдёт от месяца начисления. Пока акта нет, обязанность перечислить налог не наступила — контрольная дата поставлена в чек-лист.

**Подсказка «более поздняя дата» — только как проверка себя, не как правило.** Рядом с определённой датой уместна строка: «В двух самых частых случаях применяется более поздняя из двух дат — при обычной оплате это дата выплаты, при авансе дата начисления. Исключение — доход, отнесённый на вычеты без выплаты: там дата не связана ни с актом, ни с оплатой». Формулировать это как норму нельзя: в кодексе такого правила нет, есть отдельное правило под каждый случай.

**Курс подставляется сам.** Как только движок определил дату, курс тянется из загруженных за период. Ручной ввод остаётся, предупреждение показывается **только если подстановка не удалась** — курс за пределами загруженного периода или НБ РК недоступен. Предупреждение вместо подстановки при доступном курсе — дефект.

**Блок 2. Расчёт (разворачиваемый, кнопка «Подробнее»)**

Сумма по акту, курс, дата курса, база, ставка, сумма налога — построчно. Требования к каждой строке:

1. **Трассировка до ответа пользователя.** Не «база 4 137 000 ₸», а «7 000 EUR × 591,00 = 4 137 000 ₸, где 7 000 EUR — ваш ответ на S4.4, курс 591,00 — официальный курс НБ РК на 15.06.2026 (дата выплаты, S4.2)». Пользователь должен видеть, откуда взялось каждое число, не возвращаясь к своим ответам.
2. **Норма у каждой строки, с цитатой по клику.** Номер статьи сам по себе бесполезен: «ст. 684 п. 1» ничего не объясняет тому, кто её не помнит. По клику раскрывается сам текст нормы.
3. **Строки «что не применилось и почему» — обязательны.** Это главное, чего не хватало в первой редакции. Помогайка обязана показывать не только применённое, но и отвергнутое:
   - «Конвенция с Россией **не применена**: сертификат резидентства отсутствует (S7.2). При наличии корректного сертификата ставка составила бы 10 % вместо 15 %, налог — 700 000 ₸ вместо 1 050 000 ₸. Основание: ст. 705, ст. 10 Конвенции с РФ.»
   - «НДС за нерезидента **не начисляется**: место реализации — не РК (S6.1). Основание: ст. 454.»
   - «Освобождение по ст. 681 **не применяется**: вид услуг относится к группе, облагаемой независимо от места оказания.»

   Без этих строк пользователь видит цифру, но не видит развилки, на которой он мог сэкономить или ошибиться. Разница между 15 % и 10 % на дивидендах — это 350 000 ₸ на одной выплате, и бухгалтер должен узнать о ней здесь, а не от клиента через год.
4. **Копируется и печатается.** Блок разворачивается принудительно в печатной версии (см. §6 блок 7) и выделяется мышью целиком: он идёт в налоговый регистр как обоснование позиции.

| **R-VAT-10** | Перевозка от нерезидента: место реализации **не РК**, НДС не возникает. Для КПН — ставка 5 % как по международной перевозке | ст. 459 п. 2 пп. 5), ст. 682 п. 1 пп. 4) |

## 9. Модель данных (кратко)

```
Session
  id · user_id · role · mode · rules_version · created_at · status
  answers: JSONB            -- {questionId: value}
  verdict: JSONB            -- результат движка целиком
  flags: text[]             -- сработавшие F-*
  feedback: JSONB           -- см. §11

Operation                   -- для mode=batch
  session_id · counterparty · country · contract_ref · unk
  income_type · income_code · service_kind · place_of_supply
  act_date · payment_date · accrual_date
  amount_fx · currency · fx_rate · fx_date · base_kzt
  kpn_rate · kpn_amount · convention_applied · treaty_code
  vat_applicable · vat_base · vat_amount
  period_101_04 · period_vat

Refbook (версионируемый)
  key · version · valid_from · valid_to · payload: JSONB
  -- countries · offshore_list · conventions · convention_rates
  -- income_codes · treaty_codes · vat_place_rules · rates · mrp · deadlines
```

**Ключевое требование:** `rules_version` фиксируется на момент прохождения. При обновлении справочника старые сессии пересчитываться не должны — иначе теряется воспроизводимость.

## 10. UX-принципы

1. **Один смысловой блок — один экран.** Экран = блок S1…S9 из §4, а не отдельный вопрос: разбивать S1 на пять экранов значит порвать соответствие шаговой панели структуре ТЗ и растянуть визард до двадцати кликов. Внутри блока — не больше пяти-шести полей и только вопросы одной темы; если блок разрастается, его делят на два блока в §4, а не на два экрана внутри одного шага. *(Уточнено 19.08.2026: прежняя формулировка «один вопрос — один экран» противоречила блочной структуре §4; верна блочная.)*
2. **Подсказка всегда рядом с вариантом ответа**, а не в отдельном разделе помощи. Формат: одно предложение простым языком + ссылка «ст. 679 п. 1 пп. 3» с раскрытием цитаты по клику.
3. **Предупреждения — по ходу, не в конце.** Если пользователь выбрал «дизайнерские услуги за пределами РК», подсказка про ст. 679 п. 1 пп. 3) должна появиться **сразу**, а не в итоговом заключении. Это главная обучающая функция.
4. **Показывать промежуточный вывод.** Между блоками — плашка «Пока получается: КПН 20 %, форма 101.04 за III квартал». Пользователь видит, как ответы меняют результат. *(Отложено в v2: требует режима частичного расчёта на бэкенде — `evaluate` на неполном наборе ответов бросает `EngineError` и бросать обязан. В v1 роль промежуточной обратной связи выполняет принцип 3 — предупреждения по ходу.)*
5. **Никогда не давать голое «да/нет» по спорной норме.** Если `manual_review` — показывать сам вопрос, обе позиции и что нужно проверить.
6. **Сохранять черновик автоматически.** Возврат к незаконченной проверке через 3 дня — типичный сценарий.
7. **Терминология уровня бухгалтера.** «Налоговый агент», «облагаемый оборот», «удержание у источника» — не упрощать. Но каждый термин с тултипом.
8. **Экспорт результата** — PDF с датой, версией правил и полным нормативным обоснованием. Бухгалтер прикладывает его к налоговому регистру как обоснование позиции.

## 11. Закрытый режим — только основатель (v1)

Помогайка в первой версии не публикуется. **Сотрудникам не открывается.** Решение владельца от 19.08.2026: проверку первой версии она проводит сама.

**Доступ:**
- Отдельный feature flag не нужен — работает существующий реестр сервисов: запись `f10104` со `status: beta` и **пустым списком ролей**. Администратор видит модули в статусе beta и без выданной роли, остальные не видят.
- Проверка на сервере, не только в UI: гейт `require_service("f10104")` отдаёт **403**. Решение принято ранее и не меняется: 404 маскировал бы отказ доступа под отсутствие страницы и путал бы отладку.
- Открытие сотрудникам — отдельное решение после проверки владельцем. Технически это выдача роли на экране «Доступы», правка кода не требуется: `seed_services` создаёт запись один раз и существующую не обновляет.
- Баннер на каждом экране: «Внутренняя бета. Результаты не являются налоговой консультацией и не должны передаваться клиентам без проверки.»

**Сбор обратной связи.** Пока проверяет один человек — владелец, — экранные формы обратной связи и логирование каждого прохождения не нужны: замечания идут напрямую, по форме `FORMA-ZAMECHANIY.md`. Строить механику сбора фидбэка для одного пользователя, который и так разговаривает с разработкой ежедневно, — работа впустую.

Возвращается в план при открытии сотрудникам, и тогда целиком: поля «согласны с выводом», кнопка «отметить спорную норму», логирование `answers` + `verdict` + `rules_version` + время на каждом шаге.

**Метрики этапа:**

| Метрика | Целевое значение до открытия внешним пользователям |
|---|---|
| Число расхождений с фактически сданными формами | 0 на контрольной выборке из 20 реальных операций 2026 года |
| Закрыто блокеров P0 из §8 | 3 из 3 |
| Медианное время — типовая операция, минимальный маршрут (22 поля) | ≤ 4 минуты |
| Медианное время — полный маршрут с сертификатом (38 полей) | ≤ 8 минут, меряется отдельно |
| Спорные позиции разобраны и закрыты либо оформлены как спорные | все |

*Метрики «доля согласившихся с выводом» и «доля доведённых до результата» вступают в силу при открытии сотрудникам: на выборке из одного человека они не значат ничего.*

**Порядок валидации:**
1. Прогнать все 20 тест-кейсов из §7 — автотестами движка.
2. Взять 20 реальных операций из практики за 2026 год, прогнать через помогайку, сверить с фактически сданными формами. Расхождения разобрать поимённо.
3. Закрыть блокеры P0.
4. *(отложено)* Открыть сотрудникам — отдельным решением владельца после её собственной проверки.
5. Юридическая вычитка текстов подсказок и дисклеймера.
6. Только после этого — внешний доступ.

**Что не делать на этапе беты:** не подключать автоматическую отправку в СОНО, не сохранять данные клиентов помимо тестовых, не показывать результат без дисклеймера.
